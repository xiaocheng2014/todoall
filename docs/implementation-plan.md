# TodoAll 实施路线图

## 1. 建议技术形态

第一版建议采用一个全栈 TypeScript Web 项目：

- 响应式、移动端优先界面。
- 服务端渲染或混合渲染的 Web 框架。
- SQLite 持久化，数据库文件保存在持久化目录中。
- 数据库迁移和类型安全的数据访问层。
- 独立后台任务进程负责每日任务生成和 Bark 通知。
- Docker 化部署 Web 和后台任务，共享同一个本地 SQLite 数据库文件。
- PWA manifest 与基础离线壳；核心数据操作仍要求联网。

SQLite 采用 WAL 模式并配置写入等待时间，降低 Web 请求和后台任务同时写入时出现锁冲突的概率。第一版按单机、单应用实例部署，不把数据库文件放在网络文件系统中，也不横向启动多个应用副本。

具体框架与依赖版本在搭建脚手架时确定，避免产品文档绑定短生命周期版本。

## 2. 开发阶段

### 阶段一：工程基础和账号体系

- 初始化 Web 工程、代码质量和测试工具。
- 接入 SQLite 和数据库迁移。
- 创建首个管理员的安全初始化流程。
- 登录、退出和安全会话。
- 首次登录强制修改密码。
- 管理员用户管理、禁用和重置密码。
- 权限中间件、数据隔离测试和审计日志。

完成标准：管理员能创建用户，用户能完成首次登录和修改密码，越权访问测试通过。

### 阶段二：目标、计划和每日任务

- 目标的创建、编辑和状态管理。
- 计划创建与单次、每日、每周重复规则。
- 计划与目标多对多关联。
- 生成每日任务并保留计划快照。
- 今天页面和移动端主导航。

完成标准：三个典型示例可以正确生成任务：每天 200 个俯卧撑、每周一三五跑 5 公里、指定日期的一次性任务。

### 阶段三：分次执行和历史统计

- 快捷增加和自定义执行记录。
- 勾选、次数、时长、距离、数量任务。
- 任务状态自动计算和超额完成。
- 历史日历、累计统计、完成率和连续完成天数。
- 目标进度聚合。

完成标准：执行记录增删改后进度和状态始终一致，修改计划不影响历史任务。

### 阶段四：Bark 通知

- 用户 Bark 设置和测试通知。
- Bark 地址加密存储及界面脱敏。
- 后台通知调度进程。
- 每日 22:00 未完成摘要。
- 时间点任务提前 1 分钟提醒。
- 去重、有限重试和通知记录。

完成标准：浏览器关闭时仍能准时通知，服务重启不会重复发送成功通知。

### 阶段五：PWA 与上线准备

- PWA manifest、图标和安装体验。
- 手机端交互和无障碍检查。
- 生产环境 HTTPS、备份和日志策略。
- 性能、安全和权限回归测试。
- 部署文档与管理员操作说明。

## 3. 首轮验收场景

1. 管理员创建普通用户并设置临时密码。
2. 用户首次登录，被强制修改密码后进入“今天”。
3. 用户创建“每天做 200 个俯卧撑”，分四次记录并完成。
4. 用户创建“周一、三、五跑 5 公里”，非执行日不生成任务。
5. 用户创建“20:00 阅读 60 分钟”，在 19:59 收到 Bark 提醒。
6. 当天 22:00，系统只汇总仍未完成的任务。
7. 管理员重置密码后，用户原会话立即失效。
8. 两个普通用户无法访问彼此的任何业务数据。

## 4. 开工前需要固定的技术决策

- 全栈框架和组件库。
- 生产部署位置、SQLite 持久化目录与自动备份方式。
- 后台任务采用常驻 worker 还是平台定时任务。
- Bark 地址的服务端加密密钥管理方式。
- 首个管理员通过环境变量、命令行还是一次性初始化页面创建。

默认建议使用常驻 worker 和命令行初始化首个管理员，行为明确，也更适合精确到分钟的提醒。
